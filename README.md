# Mira Tarel0chn1tsa · eBay → Telegram

Особистий радар товарів: FastAPI, Playwright/Chromium + Firefox, BeautifulSoup, SQLite, звичайний HTML/CSS/JS і три Docker-сервіси. Англомовний адаптивний інтерфейс, вхід через Telegram, фонові перевірки та черга повідомлень.

## Запуск

У наявному `.env` уже підтримується ключ `tg=...`; перейменовувати його не потрібно. Для нового встановлення скопіюйте `.env.example` в `.env` і задайте `TELEGRAM_BOT_TOKEN`.

```bash
docker compose up -d --build
docker compose ps
```

Відкрийте [localhost:8000](http://localhost:8000). Вкажіть свій Telegram username, перейдіть за посиланням до бота, натисніть **Start** і введіть на сайті отриманий шестизначний код. Бот звіряє username з фактичним відправником Telegram і прив’язує акаунт до незмінного numeric Telegram ID. Це не пошук chat_id за довільним username: Telegram не дозволяє ботам першими починати розмову з користувачем ([документація Telegram](https://core.telegram.org/bots#how-are-bots-different-from-users)).

Додайте пошук. Перший успішний прохід збере наявні товари без повідомлень. Пошуки, результати, токени, Telegram offset і черга зберігаються в Docker volume `signal-data`. Профіль браузера worker з cookies і local storage зберігається окремо у volume `browser-data`.

За замовчуванням worker сам запускає звичайний Chromium на приватному віртуальному екрані Xvfb всередині Docker, завантажує сторінки eBay, а BeautifulSoup читає отриманий DOM. Для роботи на віддаленому сервері достатньо Docker Compose; браузер на вашому комп’ютері відкривати не потрібно. Віртуальний екран не має TCP-порту й не вимагає VNC або ручного підключення. Моніторинг працює, поки працює сервер. Початкова збірка worker завантажує Chromium, Firefox та їхні системні залежності; web і bot використовують окремий легший образ без браузерних бінарників.

```bash
docker compose logs --tail=100 web bot worker
docker compose stop
docker compose start
```

Не використовуйте `docker compose down -v`, якщо потрібно зберегти дані: `-v` видаляє volume. Один і той самий bot token має використовувати лише один polling-процес. За наявності стороннього webhook Telegram поверне 409; застосунок покаже помилку та не видалятиме чужий webhook автоматично.

## Пошуки та фільтри

Одна перевірка пошуку завантажує **лише першу сторінку результатів eBay**, відсортовану за новизною. BeautifulSoup читає всі картки з цього HTML (у перевірках — близько 60; точну кількість визначає eBay). Наступні сторінки та сторінки окремих товарів не завантажуються. Примусовий `_ipg=240` не використовується: він давав 403 у порівнянні з успішним стандартним розміром.

Фільтри передаються безпосередньо eBay:

- Ціна: `_udlo` / `_udhi`; валюта: `_curr`; категорія: `_sacat`.
- Стан: `LH_ItemCondition`; формат: `LH_BIN` / `LH_Auction`; безкоштовна доставка: `LH_FS`.
- Продавець: `_sasl` / `_saslop`; виключені слова та фрази: `_ex_kw`.
- Країна: `_salic` / `LH_LocatedIn`. Варіанти з публічної форми Advanced Search містяться в `app/ebay_filters.py`.
- Характеристики: нативні параметри eBay, наприклад `Brand=Sony`, з категорією `_dcat`. Потрібні точні назви й значення фільтрів eBay та ID категорії.

Відомі невідповідності на картках додатково відкидаються. Довільний текст локації перевіряється локально, якщо він не є підтримуваною країною. Для ціни разом із доставкою використовується лише відома вартість доставки з картки; мінімум загальної суми не підміняється мінімумом ціни без доставки. Відсутні дані не вигадуються і не спричиняють запитів сторінки товару.

На сайті доступні всі збережені поля картки: назва, посилання, ціна, валюта, фото, стан, доставка, продавець та локація, якщо вони є у видачі. `raw` містить рядки, текст і HTML-атрибути картки. Окремого завантаження характеристик немає. Дані, яких немає в списку eBay, автоматично не доповнюються.

## Новизна і Telegram

1. Перша успішна, розпізнана видача кожного нового пошуку — початковий знімок **без сповіщень**. HTTP 403, CAPTCHA або невідома розмітка не створюють порожній знімок.
2. Ідентичність — **назва + ціна з валютою + локація**. Регістр, зайві пробіли та формат `4` / `4.00` нормалізуються. ID eBay потрібен для посилання та оновлення картки, але не визначає новизну.
3. Таблиця `seen_listings` зберігає компоненти, SHA-256 індекс і користувача. Унікальність `(user_id, fingerprint)` атомарно захищає від повторів між пошуками та перезапусками. Історія залишається після видалення пошуку.
4. Із другого проходу нова комбінація, що відповідає фільтрам, створює Telegram-подію. Зміна ціни чи локації може створити нову комбінацію для того самого ID. Повернення до раніше відомої комбінації не надсилається повторно. Дата публікації не використовується.
5. Черга `notifications` зберігає окремий знімок для кожної нової комбінації. Зміна поточної ціни не змінює вже підготовленого повідомлення. Збої Telegram повторюються із затримкою. Telegram не надає idempotency key: аварія між `sendMessage` та підтвердженням у БД може дати повтор доставки.
6. Зміна критеріїв або відновлення після паузи формує новий початковий знімок без розсилки. Глобальна історія користувача зберігається.

Під час оновлення стара база мігрує транзакційно: вже збережені товари додаються до індексу без розсилки, результати та черга зберігаються. Одночасний старт web/bot/worker серіалізується через SQLite `BEGIN IMMEDIATE`.

Моніториться лише перша сторінка. Якщо між перевірками з'явиться більше збігів, ніж уміщається на ній, частину можна пропустити. Інтерфейс показує це обмеження; звужуйте фільтри або скорочуйте інтервал. «Новий збіг» означає нову для акаунта комбінацію, а не підтверджену дату створення оголошення.

## Браузер та діагностика

Основний транспорт — `EBAY_HTTP_CLIENT=playwright`: звичайний Chromium на приватному Xvfb, окремий профіль `/browser-profile`, cookies між перезапусками. Firefox використовується як резервний браузер із власним профілем `/browser-profile/firefox`. Профілі доступні тільки worker і захищені блокуванням від другого процесу. Ключі бота не передаються браузеру. Chromium працює непривілейовано з пісочницею та seccomp-профілем Docker.

Зображення, медіа, шрифти та HTML у вкладених iframe блокуються. Скрипти й стилі eBay можуть завантажуватися для роботи сторінки: один HTML списку не означає один мережевий пакет або повну відсутність службових HTTP-запитів браузера. У штатній перевірці немає переходів до `/itm/` або другої сторінки видачі.

Кожна перевірка починається з Chromium. Після 403, 503, challenge або збою/таймауту браузера виконується одна спроба тієї самої сторінки через Firefox. Якщо Chromium успішний, Firefox не запускається. Перед запуском іншого браузера попередній закривається зі збереженням профілю. Native User-Agent відповідає реальному рушію; cookies між браузерами не копіюються. `EBAY_FIREFOX_FALLBACK=false` вимикає резервний браузер.

Між завантаженнями сторінок — випадкова пауза **10–20 секунд** (`REQUEST_DELAY_SECONDS` + випадкове значення до `REQUEST_DELAY_JITTER_SECONDS`), спільна для всіх пошуків і переходу до Firefox. Якщо обидва браузери не отримали доступ — спільна пауза щонайменше 15 хвилин. HTTP 429 одразу вмикає спільну паузу без спроби іншим браузером. Довший `Retry-After` враховується до 24 годин; якщо обидва браузери заблоковані, береться довший строк. Для помилок доступу немає додаткової експоненційної затримки окремих пошуків: активні пошуки, що вже чекали або мали помилку, вирівнюються на спільний строк. Пошук із пізнішим звичайним розкладом зберігає свій інтервал. Автоматичного скидання профілів та розв'язування CAPTCHA немає. Доступ eBay залишається нестабільним; це обмеження зовнішнього сервісу не приховується порожніми успішними результатами.

Жива діагностика також читає першу сторінку з тією самою логікою резервного браузера без змін БД та повідомлень:

```bash
docker compose exec worker python -m app.diagnostics --watch-id 1
docker compose exec worker python -m app.diagnostics --client curl_cffi --query Clothes
```

За замовчуванням використовується тимчасовий діагностичний профіль. Не передавайте `/browser-profile`, коли worker працює. Щоб перевірити саме робочу сесію, зупиніть worker, виконайте `docker compose run --rm --no-deps worker python -m app.diagnostics --watch-id 1 --profile-dir /browser-profile`, потім запустіть worker. `last-error.png` і `last-error.json` у профілі містять знімок останньої помилки.

Для перевірки розмітки збережіть отриману сторінку HTML і запустіть:

```bash
uv run python scripts/inspect_html.py /path/to/search.html
```

## Авторизація та розгортання

Access JWT діє 10 хвилин і зберігається лише в пам’яті вкладки. Refresh token — випадковий одноразовий секрет у `HttpOnly`, `SameSite=Strict` cookie; у БД зберігається HMAC-хеш. Оновлення автоматичне, з ротацією та відкликанням сім’ї за повторного використання. Після reload фронт отримує access через refresh endpoint. Вкладки серіалізують оновлення через Web Locks; для старих браузерів без Web Locks рекомендовано одну активну вкладку. Вихід відкликає refresh-сесію; уже виданий access живе до свого строку завершення.

Код одноразовий: 10 хвилин, 5 спроб, обмеження запитів username/IP. На API перевіряється власник кожного пошуку та товару. Origin-перевірка для мутацій, CSP, безпечне відображення тексту eBay. Логи HTTP-клієнта вимкнені, щоб URL Telegram не розкрив токен. `.env` не комітиться й не копіюється в Docker-образ; на VPS Actions створює його з секрету `APP_ENV`.

Локально порт доступний лише на `127.0.0.1:8000`. Для VPS є `compose.traefik.yaml`: мережа `traefik-public`, HTTPS через `websecure` / `myresolver`, домен `miratarelochnitsa.store`, без публікації портів застосунку. GitHub Actions тестує код і деплоїть у `/opt/mira-tarel0chn1tsa`, створюючи серверний `.env` із секрету `APP_ENV`. Налаштування DNS і потрібних GitHub Secrets описані в [інструкції деплою](docs/deployment.md).

Індикатор внизу sidebar (на мобільному — закріплений унизу екрана) показує поточний браузер під час перевірки та стан моніторингу: перевірка, наступна спроба, спільна пауза eBay з часом, призупинені пошуки або недоступний worker. Стан Telegram показується окремим рядком за наявності проблеми. Спільна пауза зберігається в SQLite та відновлюється після перезапуску worker; жива heartbeat більше не означає успішний доступ до eBay.

| Змінна | Типове значення | Призначення |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` / `tg` | — | Секрет бота |
| `TELEGRAM_BOT_USERNAME` | через `getMe` | Необов’язковий username без @ |
| `PUBLIC_URL` | `http://localhost:8000` | Дозволений браузерний Origin |
| `COOKIE_SECURE` | `false` | `true` для HTTPS |
| `SECRET_KEY` | створюється в `/data/secret.key` | Власний ключ мінімум 32 символи; має бути однаковим у всіх процесах |
| `REQUEST_DELAY_SECONDS` | `10` | Мінімальна пауза після завершення запиту сторінки eBay |
| `REQUEST_DELAY_JITTER_SECONDS` | `10` | Випадкова добавка від 0 до цього значення; `0` для фіксованої паузи |
| `EBAY_HTTP_CLIENT` | `playwright` | Chromium → Firefox; альтернативи `curl_cffi` та `httpx` |
| `EBAY_FIREFOX_FALLBACK` | `true` | Одна резервна спроба Firefox після збою Chromium |
| `EBAY_BROWSER` | `chrome` | Тільки TLS/HTTP-профіль альтернативи curl_cffi |
| `EBAY_BLOCK_COOLDOWN_SECONDS` | `900` | Спільна пауза після обмеження доступу |
| `EBAY_BROWSER_PROFILE_DIR` | `data/browser-profile`; `/browser-profile` у Compose | Chromium у корені; окремий профіль Firefox у підкаталозі `firefox` |
| `EBAY_BROWSER_HEADLESS` | `false` | Обидва браузери на автоматичному Xvfb; `true` для headless |
| `EBAY_BROWSER_TIMEOUT_SECONDS` | `45` | Ліміт часу навігації браузера |
| `EBAY_PROXY` | порожньо | HTTP(S)-proxy для eBay; Telegram використовує пряме підключення |

Compose задає `DATABASE_URL=sqlite:////data/ebay.db` і `STATE_DIR=/data` для всіх процесів. SQLite працює з WAL, foreign keys та busy timeout. Це інсталяція на одному Docker-хості: по одному worker та bot, з блокуванням повторних екземплярів через спільний volume. Масштабування між хостами потребує PostgreSQL, розподілених блокувань і відповідних міграцій. Поточна версія автоматично створює схему та мігрує попередню чергу сповіщень.

## Розробка та перевірки

Потрібен Python 3.12+; `uv.lock` і `requirements.lock` фіксують залежності.

```bash
uv sync --dev --locked
uv run playwright install chromium
uv run pytest -q
uv run uvicorn app.main:app --reload
# Окремі термінали, та сама папка і .env:
uv run python -m app.bot
uv run python -m app.worker
```

Тести використовують окрему тимчасову БД та підставні Telegram/eBay/Playwright-клієнти. Вони не пишуть реальним користувачам і не змінюють робочу базу. Перевіряють парсер обох розміток, довільні характеристики, гроші/валюти, критерії, перший знімок без повідомлень, складений індекс, зміну цін, дедуплікацію між пошуками, знімки outbox, міграцію БД, повторні сканування, backoff, ізоляцію акаунтів, OTP, ротацію токенів і CRUD. Окремо перевірені повторне використання браузерного контексту, блокування зайнятого профілю, закриття/відновлення браузера, CAPTCHA, мережеві обмеження та виключення секретів з оточення браузера. Для unit-тестів браузерний бінарник не потрібен. API: `/docs`; стан вебпроцесу: `/api/health`; стан bot/worker після входу: `/api/status`.


Перевірка інтерфейсу з ізольованими API-fixtures (без змін робочої БД і надсилання повідомлень):

```bash
uv run python scripts/check_ui.py --url http://localhost:8000 --output /tmp/mira-ui
```

Сценарій перевіряє вхід і код, створення та редагування пошуку, підтвердження видалення, оновлення характеристик, відновлення з’єднання, вихід і мобільну верстку. Знімки екрана зберігаються в каталозі `--output`.
