# Signal · eBay → Telegram

Особистий радар товарів: FastAPI, Playwright/Chromium, BeautifulSoup, SQLite, звичайний HTML/CSS/JS і три Docker-сервіси. Український адаптивний інтерфейс, вхід через Telegram, фонові перевірки та черга повідомлень.

## Запуск

У наявному `.env` уже підтримується ключ `tg=...`; перейменовувати його не потрібно. Для нового встановлення скопіюйте `.env.example` в `.env` і задайте `TELEGRAM_BOT_TOKEN`.

```bash
docker compose up -d --build
docker compose ps
```

Відкрийте [localhost:8000](http://localhost:8000). Вкажіть свій Telegram username, перейдіть за посиланням до бота, натисніть **Start** і введіть на сайті отриманий шестизначний код. Бот звіряє username з фактичним відправником Telegram і прив’язує акаунт до незмінного numeric Telegram ID. Це не пошук chat_id за довільним username: Telegram не дозволяє ботам першими починати розмову з користувачем ([документація Telegram](https://core.telegram.org/bots#how-are-bots-different-from-users)).

Додайте пошук. Перший успішний прохід збере наявні товари без повідомлень. Пошуки, результати, токени, Telegram offset і черга зберігаються в Docker volume `signal-data`. Профіль браузера worker з cookies і local storage зберігається окремо у volume `browser-data`.

За замовчуванням worker сам запускає звичайний Chromium на приватному віртуальному екрані Xvfb всередині Docker, завантажує сторінки eBay, а BeautifulSoup читає отриманий DOM. Для роботи на віддаленому сервері достатньо Docker Compose; браузер на вашому комп’ютері відкривати не потрібно. Віртуальний екран не має TCP-порту й не вимагає VNC або ручного підключення. Моніторинг працює, поки працює сервер. Початкова збірка worker завантажує Chromium та системні залежності; web і bot використовують окремий легший образ без браузерних бінарників.

```bash
docker compose logs --tail=100 web bot worker
docker compose stop
docker compose start
```

Не використовуйте `docker compose down -v`, якщо потрібно зберегти дані: `-v` видаляє volume. Один і той самий bot token має використовувати лише один polling-процес. За наявності стороннього webhook Telegram поверне 409; застосунок покаже помилку та не видалятиме чужий webhook автоматично.

## Пошуки та характеристики

- Ключові слова eBay, ціна від/до, валюта, стан, аукціон / «Купити зараз».
- Локація товару та продавець: входження тексту англійською без урахування регістру.
- Безкоштовна доставка, врахування відомої вартості доставки у фільтрі ціни, виключення слів/фраз.
- Категорія eBay та довільні характеристики: `Brand=Sony`, `Color=Silver`, `Storage Capacity=256 GB` тощо. Для кожної характеристики задається назва й текст, який має входити у значення.
- Період перевірки від 60 секунд; це цільовий інтервал, а фактична частота залежить від кількості пошуків і затримок eBay.
- Редагування, пауза / відновлення, ручна перевірка, видалення пошуку, окрема вкладка нових товарів, пагінація, вікно подробиць.

Поля картки: ID, назва, посилання, фото, ціна/валюта, доставка, стан, продавець, локація, формат, дата публікації за наявності, довільний словник Item specifics. У подробицях є всі отримані JSON-LD, метадані, текстові рядки картки та її HTML-атрибути. Нові назви характеристик не потребують зміни схеми БД. Окреме фото чи характеристика можуть бути відсутні в HTML; відсутні дані не вигадуються. Опис продавця у сторонньому iframe зберігається як URL, але його скрипти та HTML не виконуються. Приховані/API-only дані та всі варіанти товару не гарантуються HTML-парсером.

Першими показуються товари, для яких перевірені всі задані фільтри. Якщо для перевірки потрібна сторінка товару, запис залишається в черзі характеристик. Відомі невідповідності відкидаються. Невідома доставка не вважається безкоштовною; валюти не конвертуються. Ціни без доставки не включають податки та імпортні збори. Географія доставки відповідає публічній видачі eBay цього сервера, без авторизації eBay.

## Як відокремлюємо нові оголошення

1. До першої успішної перевірки пошук перебуває у стані ініціалізації. Усі налаштовані сторінки мають успішно завантажитися та розпізнатися. HTTP 403, CAPTCHA та невідома розмітка не створюють порожній початковий знімок.
2. Усі товари першого проходу позначаються `baseline`. Вони відображаються на сайті, але **ніколи не створюють Telegram-повідомлень у цьому пошуку**.
3. Товар, знайдений пізніше, надсилається лише якщо відповідає фільтрам і HTML містить підтверджену дату публікації після `tracking_since`. Перше виявлення не підміняє дату публікації. Тому місячне оголошення з далекої сторінки не стане «новим».
4. **Якщо eBay не віддає точну дату публікації, товар показується зі статусом «Дату не підтверджено» без сповіщення.** Це свідомий компроміс на користь вимоги не надсилати старі оголошення; частина справді нових товарів також може залишитися без повідомлення. HTML eBay не забезпечує універсального доказу новизни.
5. Зміна критеріїв очищає результати цього пошуку й формує новий baseline. Відновлення після паузи теж формує новий знімок: товари за час паузи не розсилаються заднім числом.
6. Унікальний запис `(watch_id, ebay_id)` і одна outbox-подія на товар захищають від повторних повідомлень під час звичайних повторних сканувань і перезапусків. При збої Telegram повідомлення повторюється із затримкою. Telegram не має idempotency key: аварія між успішним `sendMessage` і записом підтвердження в БД може дати дубль. Різні пошуки можуть окремо повідомити про один товар.

Історія знахідок залишається доступною. «Востаннє бачили» не гарантує, що оголошення досі активне. Доступність і фінальну ціну потрібно перевірити на eBay. Широкі запити можуть перевищувати вікно сканування: інтерфейс покаже попередження про ліміт сторінок. Для точніших результатів звузьте критерії.

## Парсер та доступ до eBay

Основний транспорт — `EBAY_HTTP_CLIENT=playwright`. Профіль `/browser-profile` монтується тільки у worker. Після звичайного перезапуску сесія зберігається; два процеси не можуть одночасно відкрити цей профіль. Worker коректно закриває браузер при SIGTERM. `shm_size: 1gb` і офіційний seccomp-профіль дозволяють запуск від непривілейованого користувача з увімкненою пісочницею Chromium.

Браузер залишається відкритим між перевірками. Під час закриття додатково зберігається приватний `session-state.json` з правами 0600: так відновлюються також cookies без строку дії, які Chromium може видаляти після завершення сесії. Не публікуйте вміст цього файлу чи профілю.

Під час живої перевірки 21 жовтня 2026 року headless Chromium отримав 403, а звичайний Chromium на Xvfb із тим самим профілем прочитав усі **10 оголошень збереженого пошуку** та **6 характеристик** першого товару без проксі. Саме тому `EBAY_BROWSER_HEADLESS=false` є типовим режимом. Повторний запуск також отримував 403: доступ залишається нестабільним. Успішний прохід не є гарантією постійного доступу; Playwright не можна вважати повним вирішенням блокування eBay.

Після запуску постійного worker з автоматичним Xvfb завершився успішний фоновий прохід: **10 збережених товарів, подробиці всіх 10 оновлені, помилка пошуку очищена**. Окремо в остаточному Docker-образі перевірено відновлення cookie без строку дії після закриття та нового запуску браузера. Тимчасові 403 при наступних перевірках усе ще можливі.

Браузер використовує окремий профіль застосунку. Не вказуйте профіль вашого особистого Chrome. Ключ бота й SECRET_KEY не передаються в оточення Chromium. Навігація обмежена `www.ebay.com`, ресурси — доменами eBay. Сторонні рекламні домени, завантаження файлів і service workers вимкнено. Жоден порт керування браузером не публікується.

Playwright не гарантує усунення CAPTCHA чи IP-блокувань. При сторінці перевірки браузер зберігає `last-error.png` та `last-error.json` у своєму профілі, а всі пошуки роблять паузу. CAPTCHA автоматично не розв’язується. Не потрібно повторно запускати діагностику в циклі, поки eBay вимагає паузу.

Деталі селекторів і меж перевірки — у [docs/parser.md](docs/parser.md). Початковий `httpx` із User-Agent `EbaySignal` отримував **403**. Під час повторної діагностики 21 жовтня 2026 року безкоштовний `curl_cffi` з браузерним TLS/HTTP-профілем Chrome без проксі успішно завантажив живу видачу на **240 оголошень** та сторінку товару з характеристиками. Зміна лише User-Agent у `httpx` давала як 200, так і 403, тому основний клієнт — `curl_cffi`. Це не гарантує постійного доступу: eBay може знову обмежити мережу або сесію.

HTTP-сесія повторно використовує отримані від eBay cookies; штучний cookie `dp1` прибрано. Запити деталей містять Referer пошуку. Звичайні редиректи в межах HTTPS eBay підтримуються; редиректи на CAPTCHA/challenge не виконуються. Після 403/429/503 або розпізнаної сторінки перевірки діє **спільна пауза всіх пошуків на 15 хвилин**. Довший `Retry-After` враховується до 24 годин. Час наступної спроби зберігається в БД пошуку.

Перевірка з контейнера (одна сторінка пошуку та, з `--detail`, один товар; без змін БД чи повідомлень). За замовчуванням діагностика створює тимчасовий профіль, щоб не конфліктувати з worker:

```bash
docker compose exec worker python -m app.diagnostics --detail
# Критерії конкретного збереженого пошуку, до трьох сторінок:
docker compose exec worker python -m app.diagnostics --watch-id 1 --pages 3 --detail
# Порівняння з httpx за потреби:
docker compose exec worker python -m app.diagnostics --client httpx
# Інший безкоштовний TLS/HTTP-профіль, без зміни робочої конфігурації:
docker compose exec -e EBAY_BROWSER=safari worker python -m app.diagnostics --client curl_cffi --detail
```

Для окремого профілю діагностики, який зберігається між її запусками в контейнері: `--profile-dir /tmp/ebay-diagnostic-profile`. Не передавайте `/browser-profile`, коли worker працює: профіль зайнятий. Щоб перевірити саме робочу сесію, зупиніть worker, виконайте `docker compose run --rm --no-deps worker python -m app.diagnostics --watch-id 1 --profile-dir /browser-profile --detail`, потім запустіть worker. Знімок помилки можна отримати через `docker compose cp worker:/browser-profile/last-error.png ./data/ebay-last-error.png`.

Повернення до HTTP-клієнта: задайте `EBAY_HTTP_CLIENT=curl_cffi` у `.env` і виконайте `docker compose up -d worker`. Профіль браузера залишиться у volume для наступного використання.

Якщо обидва клієнти знову бачать 403, спочатку порівняйте зі звичайним браузером у тій самій мережі, перевірте VPN та зачекайте завершення паузи. Для іншого мережевого середовища можна налаштувати `EBAY_PROXY`; платний сервіс не є вимогою. Збережені знахідки під час обмеження доступні.

Для перевірки розмітки збережіть отриману сторінку HTML і запустіть:

```bash
uv run python scripts/inspect_html.py /path/to/search.html
uv run python scripts/inspect_html.py /path/to/item.html --item-url https://www.ebay.com/itm/123456789001
```

## Авторизація та розгортання

Access JWT діє 10 хвилин і зберігається лише в пам’яті вкладки. Refresh token — випадковий одноразовий секрет у `HttpOnly`, `SameSite=Strict` cookie; у БД зберігається HMAC-хеш. Оновлення автоматичне, з ротацією та відкликанням сім’ї за повторного використання. Після reload фронт отримує access через refresh endpoint. Вкладки серіалізують оновлення через Web Locks; для старих браузерів без Web Locks рекомендовано одну активну вкладку. Вихід відкликає refresh-сесію; уже виданий access живе до свого строку завершення.

Код одноразовий: 10 хвилин, 5 спроб, обмеження запитів username/IP. На API перевіряється власник кожного пошуку та товару. Origin-перевірка для мутацій, CSP, безпечне відображення тексту eBay. Логи HTTP-клієнта вимкнені, щоб URL Telegram не розкрив токен. `.env` не копіюється в образ і не потрапляє у вихідні артефакти.

За замовчуванням порт доступний лише на `127.0.0.1:8000`. Для зовнішнього сервера поставте HTTPS reverse proxy, налаштуйте `PUBLIC_URL=https://your-domain.example` і `COOKIE_SECURE=true`. Не відкривайте Docker socket. Публікація в інтернет, домен і TLS у цей проєкт не входять.

| Змінна | Типове значення | Призначення |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` / `tg` | — | Секрет бота |
| `TELEGRAM_BOT_USERNAME` | через `getMe` | Необов’язковий username без @ |
| `PUBLIC_URL` | `http://localhost:8000` | Дозволений браузерний Origin |
| `COOKIE_SECURE` | `false` | `true` для HTTPS |
| `SECRET_KEY` | створюється в `/data/secret.key` | Власний ключ мінімум 32 символи; має бути однаковим у всіх процесах |
| `REQUEST_DELAY_SECONDS` | `5` | Мінімальна пауза між HTTP-запитами eBay |
| `EBAY_HTTP_CLIENT` | `playwright` | Chromium; альтернативи `curl_cffi` та `httpx` |
| `EBAY_BROWSER` | `chrome` | Тільки TLS/HTTP-профіль альтернативи curl_cffi |
| `EBAY_BLOCK_COOLDOWN_SECONDS` | `900` | Спільна пауза після обмеження доступу |
| `EBAY_BROWSER_PROFILE_DIR` | `data/browser-profile`; `/browser-profile` у Compose | Профіль Chromium з cookies/local storage |
| `EBAY_BROWSER_HEADLESS` | `false` | Звичайний Chromium на автоматичному Xvfb; `true` для headless |
| `EBAY_BROWSER_TIMEOUT_SECONDS` | `45` | Ліміт часу навігації браузера |
| `MAX_SEARCH_PAGES` | `3` | До 240 оголошень на сторінку, якщо eBay приймає `_ipg=240` |
| `DETAILS_PER_SCAN` | `12` | Ліміт запитів деталей за один прохід |
| `EBAY_PROXY` | порожньо | HTTP(S)-proxy для eBay; Telegram використовує пряме підключення |

Compose задає `DATABASE_URL=sqlite:////data/ebay.db` і `STATE_DIR=/data` для всіх процесів. SQLite працює з WAL, foreign keys та busy timeout. Це інсталяція на одному Docker-хості: по одному worker та bot, з блокуванням повторних екземплярів через спільний volume. Масштабування між хостами потребує PostgreSQL, розподілених блокувань і міграцій. Зміни схеми для наступних версій потребуватимуть міграцій; поточна версія створює початкову схему автоматично.

## Розробка та перевірки

Потрібен Python 3.12+; `uv.lock` і `requirements.lock` фіксують залежності.

```bash
uv sync --dev --locked
uv run playwright install chromium
uv run pytest -q
uv run uvicorn app.main:app --reload
# Окремі термінали, та сама папка і .env:
uv run python -m app.bot
uv run python -m app.worker
```

Тести використовують окрему тимчасову БД та підставні Telegram/eBay/Playwright-клієнти. Вони не пишуть реальним користувачам і не змінюють робочу базу. Перевіряють парсер обох розміток, довільні характеристики, гроші/валюти, критерії, baseline, дату публікації, outbox, повторні сканування, backoff, ізоляцію акаунтів, OTP, ротацію токенів і CRUD. Окремо перевірені повторне використання браузерного контексту, блокування зайнятого профілю, закриття/відновлення браузера, CAPTCHA, мережеві обмеження та виключення секретів з оточення браузера. Для unit-тестів браузерний бінарник не потрібен. API: `/docs`; стан вебпроцесу: `/api/health`; стан bot/worker після входу: `/api/status`.
